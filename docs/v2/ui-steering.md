# Explicit steering UI

Imports only Core34 `steering.rs` from `63366a487` with its export registration, in a separate provenance commit. The UI uses the root-selected ordinary POST `/api/v2/conversations/{id}/steer` and GET `/api/v2/conversations/{id}/steering/{request_key}`. No shared server, workspace manifest or lock changes are included.

A new explicit Steer action requires fresh valid Running status, current steer capability and positive sampled control revision. Ordinary Send remains unchanged ordered intake. Uncertain failure retains exact text/key/run/projection/control revisions, even if lease renewal turns capability off. Definitive refusal requires explicit review for a new request. Editing the visible text never mutates the frozen retry. A separate Check delivery action reads private status; reserved/queued/unknown/ACK/rejected are distinct, and ACK never means completion. Unsupported/ordered receipts explicitly explain queued fallback.

Mounted state is keyed by authenticated session generation, conversation, exact run and selection generation. Navigation or auth/scope change discards this private steering state; delayed callbacks check both generations and component lifetime. Owned POST/GET AbortControllers receive teardown and a finite deadline. Same-origin cookies, CSRF, bounded response reads, strict fixed paths and no-store are retained. Neither bearer transport nor Worker conversion is introduced.

Validation: four focused Rust behavior tests and six Node bridge tests passed; locked web+execution-controls WASM check and strict Clippy passed. These test request immutability, refused capability/phase/control/text, foreign scope/run retry refusal, exact receipt/status binding, delivery distinctions, request authentication shape, wrong paths/methods, teardown/deadline abort and malformed/oversized responses. No actual mounted-browser, provider delivery or completion qualification is claimed.
